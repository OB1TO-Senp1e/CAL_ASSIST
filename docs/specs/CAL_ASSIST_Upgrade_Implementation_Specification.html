Prepared from the CAL_ASSIST architecture and requirements supplied in the project brief.

1. Executive Summary

CAL_ASSIST should remain a Personal Time Operating System rather than becoming a conventional calendar. The upgrade adds a Coordination layer that manages the administrative lifecycle around meetings: understand intent, find feasible times, obtain approval where required, create calendar/Google Meet events, track confirmations, prepare briefs, monitor execution, and create follow-up tasks.

Target lifecycle: Intent → Understand → Plan → Coordinate → Schedule → Confirm → Execute → Reality Detection → Replan → Follow-up → Learn.

2. Existing Architecture to Preserve

Core engines: Context Engine, Memory Engine, Assistant Orchestrator. AI engines: Intent Parser, Planning Engine, Scheduling Engine, Reality Engine, Replanning Engine. Domain engines: Goal Engine, Commitment Engine, Project Engine, Task Engine.

Existing principles remain mandatory: strong typing, Zod validation, explicit autonomy controls, explainability/audit logs, pluggable providers, production-quality testing and type safety.

3. New Engines and Modules

Add Coordination Engine, Meeting Engine, Availability Engine, Confirmation Engine, Reminder Engine, Briefing Engine, Follow-up Engine, and Preference Engine. These should be domain/application services, not LLM-only behaviors.

4. Product Capabilities

Natural-language scheduling; availability search; hard/soft constraints; Google Calendar sync; Google Meet creation; attendee management; approval gates; invitation drafting; confirmation tracking; reminders; recurring meetings; time-zone intelligence; meeting templates; executive preferences; meeting briefs; agenda generation; post-meeting follow-up; action-item extraction; task creation; reality detection; intelligent replanning; daily briefings.

Core user promise: “Tell CAL_ASSIST what needs to happen; it coordinates the work around your time while keeping you in control of consequential actions.”

5. Google Integration

Use Google OAuth 2.0 for account authorization. Store access/refresh tokens encrypted server-side. Do not expose refresh tokens to the browser.

Create a provider abstraction so Google is an adapter rather than a hard-coded dependency. The Google Calendar adapter should support calendar discovery, event listing, event creation/update/deletion, attendee handling, availability lookup, recurrence, and Google Meet conference creation.

For Meet-enabled events, request Calendar conference data using the Google Meet conference solution. Persist the provider event ID, conference ID/code where available, and join URL.

Recommended scopes should be minimized to the features actually enabled. Request broader Calendar write scope only when required by the user's enabled workflow.

6. Provider Interface

TypeScript contract:
interface CalendarProvider {
  listCalendars(): Promise<Calendar[]>;
  listEvents(query: EventQuery): Promise<CalendarEvent[]>;
  createEvent(input: CreateEventInput): Promise<CalendarEvent>;
  updateEvent(id: string, input: UpdateEventInput): Promise<CalendarEvent>;
  deleteEvent(id: string): Promise<void>;
  findAvailability(input: AvailabilityQuery): Promise<AvailabilityResult>;
}
Conference support should be provider-neutral:
conference: { enabled: boolean; provider: 'google_meet' | 'none' | string }.

7. Meeting Lifecycle

DRAFT → PROPOSED → PENDING_APPROVAL → SCHEDULED → INVITATIONS_SENT → PARTIALLY_CONFIRMED → CONFIRMED → IN_PROGRESS → COMPLETED → FOLLOW_UP → CLOSED.

Additional terminal/intermediate states: DECLINED, CANCELLED, RESCHEDULED, NO_SHOW, FAILED.

8. Database Model

Recommended new Prisma entities: CalendarConnection, Meeting, MeetingParticipant, MeetingProposal, SchedulingPreference, MeetingTemplate, Reminder, MeetingBrief, FollowUp, AiActionLog. Reuse existing Event, Commitment, Task, Project, Goal and User entities where appropriate.

Example Meeting fields: id, userId, eventId, title, description, status, durationMinutes, timezone, meetingType, conferenceProvider, conferenceUrl, conferenceId, createdAt, updatedAt.

MeetingParticipant: id, meetingId, name, email, role, responseStatus, required, respondedAt.

MeetingProposal: id, meetingId, start, end, score/priority if used internally, reasons, conflicts, createdAt. Expose human-readable reasons instead of opaque scores.

9. Autonomy and Approval

Implement granular permissions instead of a single AI autonomy switch: calendar.read, calendar.create, calendar.update, calendar.delete, meeting.create, meeting.reschedule, meeting.cancel, email.draft, email.send, reminder.create, external_contact.

Recommended levels: Suggest only; Prepare drafts; Ask before external action; Auto-schedule; Auto-coordinate. External communication and destructive calendar changes should default to approval unless explicitly enabled.

Every execution path must pass permission checks and write an audit record.

10. Natural-Language Scheduling

Example: “Arrange a 45-minute call with ABC next week, preferably Tuesday afternoon, use Google Meet.” The Intent Parser should produce structured JSON validated by Zod. The LLM should not directly call Google APIs.

Example structured intent:
{ intent: 'schedule_meeting', durationMinutes: 45, dateRange: {from, to}, preferredTime: {period:'afternoon'}, participants:[...], conference:{provider:'google_meet'} }

Execution path: LLM → structured intent → Zod validation → permission check → Coordination Engine → Availability Engine → Scheduling Engine → approval → Calendar provider.

11. Availability and Scheduling

Hard constraints: existing events, required attendees, working hours, time zones, explicit blocked periods, commitments. Soft constraints: preferred hours, meeting duration, buffers, lunch, focus time, meeting density, learned preferences.

Return multiple candidate slots with explanations. Example: “Wednesday 3:30–4:15 PM — all required participants available; within preferred afternoon window; 15-minute buffer preserved.”

Avoid opaque AI-only ranking. Deterministic constraints should be enforced in application code; AI can interpret preferences and explain results.

12. Executive/Boss Mode

Allow a user to define working hours, preferred meeting times, minimum buffer, maximum meetings/day, lunch window, focus hours, default duration, preferred timezone, and preferred conference provider.

Support per-meeting-type rules such as client=45 minutes, internal=30 minutes, interview=60 minutes, board=60 minutes.

Distinguish explicit preferences from learned patterns. Learned behavior should be proposed as a suggestion, not silently converted into a hard rule.

13. Templates, Invitations, Confirmations & Reminders

Templates should store duration, conference provider, agenda starter, buffers and reminder rules. Provide Client Meeting, Interview, Internal Standup and Board Meeting templates as examples.

Invitation engine should generate professional drafts and optionally send via a connected provider after approval.

Confirmation engine tracks PENDING, ACCEPTED, DECLINED, TENTATIVE and UNKNOWN. Dashboard should show counts and prompt follow-up when appropriate.

Reminder engine supports 24h, 1h, 15m and custom reminders, with in-app/email/push channels as available.

14. Meeting Briefing and Follow-up

Briefing engine combines Context Engine + Memory Engine + meeting data to produce purpose, participants, prior interactions, open items, suggested agenda and relevant tasks.

Follow-up engine turns notes into proposed action items, owners, due dates and email drafts. Require confirmation before creating externally assigned tasks or sending messages.

Example: “Rahul will send the revised proposal by Friday” → proposed task with owner Rahul, due Friday, linked to the meeting/project.

15. Reality Engine Integration

Use actual execution data to compare planned vs actual. Detect overruns, early finishes, missed meetings, no-shows and downstream schedule impact.

Example: a 30-minute meeting runs 18 minutes over. Reality Engine reports the deviation; Replanning Engine proposes moving subsequent flexible blocks while protecting hard commitments and buffers.

16. Replanning

When a user reports “I’m running 30 minutes late,” calculate affected events/tasks/commitments and propose a new plan. Never silently change consequential external commitments unless autonomy rules permit it.

Proposal format should list impacted items, proposed new times, conflicts and why the changes were chosen.

18. Security

Encrypt OAuth tokens at rest. Use short-lived access tokens where possible, refresh securely, and revoke connections cleanly. Apply least-privilege scopes. Validate every request with Zod. Enforce ownership/authorization at service level, not only controller level.

Protect against prompt injection from calendar descriptions, event titles, emails and notes. Treat external text as untrusted data. Never allow external content to redefine permissions or tool policy.

Audit permission checks, proposals, approvals, executions, provider errors and user overrides. Do not store private chain-of-thought; store concise operational reasoning summaries.

19. Frontend

Recommended screens/components: Ask CAL_ASSIST composer; Schedule Meeting modal; Candidate Slots panel; Meeting Detail; Calendar Connections; Executive Preferences; Autonomy Controls; Meeting Dashboard; Meeting Brief; Follow-up panel; Daily Briefing.

Ask composer should show what CAL_ASSIST understood before execution. Every external or destructive action should have a visible approval state.

20. Example End-to-End Workflow

User: “Boss wants a 45-minute meeting with ABC Agency next Wednesday afternoon with Rahul and Priya.” CAL_ASSIST parses intent, loads preferences, checks calendars, proposes slots, creates a proposal, requests approval if needed, creates Google Calendar + Meet, tracks responses, prepares a brief, and later converts outcomes into follow-up tasks.

This should feel like an executive assistant workflow, not a form-driven calendar workflow.

21. Implementation Roadmap

Phase 1: Google OAuth, Calendar provider abstraction, event sync, Meet creation, Meeting entity, participants, availability, proposals, autonomy and approval gates.

Phase 2: Natural-language scheduling, preferences, templates, invitation drafts, confirmation tracking, reminders, recurring meetings and timezone support.

Phase 3: Meeting briefs, agenda generation, memory integration, follow-ups, action-item extraction, task creation and daily briefing.

Phase 4: Reality detection, overrun detection, commitment impact analysis, intelligent replanning and learned preferences.

22. Testing & Acceptance Criteria

Unit tests: intent schemas, constraint evaluation, availability intersection, timezone conversions, permission checks, lifecycle transitions, provider mapping, recurrence handling.

Integration tests: OAuth connection, Calendar event creation/update/delete, Meet conference creation, attendee responses, token refresh and failure recovery.

E2E acceptance: natural-language request produces a validated proposal; approval is required when configured; approved request creates event and Meet; participant state is tracked; reminder fires; meeting completion can produce follow-up tasks.

Security tests: cross-user access denial, invalid tokens, malicious event descriptions, unauthorized tool calls, approval bypass attempts.

Performance: retain the existing frontend bundle budget and loopback API smoke benchmark. Add benchmarks for availability queries, event synchronization and meeting proposal generation.

23. Free-First Strategy

Keep core individual productivity free: Google Calendar connection, Google Meet creation, natural-language scheduling, availability/conflict detection, templates, recurring meetings, reminders, agenda generation, meeting briefs, basic follow-up and daily schedule.

Potential paid layer should focus on organizational scale: shared assistants, team scheduling, admin controls, advanced integrations, audit/compliance features, organization-wide policies and higher AI usage limits.

24. Prioritized Backlog

P0: Google OAuth; provider interface; Google Calendar adapter; Meet creation; Meeting model; participant model; availability engine; approval/autonomy; audit logging; basic UI.

P1: natural-language scheduling; preferences; templates; confirmations; reminders; timezone handling; recurring meetings; invitation drafts.

P2: briefs; agendas; memory-aware context; follow-up; task extraction; daily briefing.

P3: reality-driven replanning; learned preferences; multi-provider coordination; advanced organization workflows.

25. Migration Plan

1. Add database migrations without removing existing Event/Task/Commitment models. 2. Introduce provider interfaces and mock adapter. 3. Add Google connection storage and OAuth flow. 4. Add Meeting as a domain object linked to Event. 5. Route new meeting creation through Coordination Engine while retaining /events for legacy clients. 6. Add audit/autonomy enforcement. 7. Add UI incrementally. 8. Backfill only safe relationships from existing events after validation.

26. Definition of Done

A release is complete when a user can connect Google, ask CAL_ASSIST in natural language to arrange a meeting, see what was understood, receive feasible slots with explanations, approve or reject execution, create a Google Calendar event with a Google Meet link, invite attendees, track responses, receive reminders, open a meeting brief, and create follow-up tasks — with permissions, audit logs, validation, error handling and tests covering the workflow.

Appendix B — Engineering Rule

AI proposes and interprets; deterministic services validate and execute.
This rule should govern calendar changes, permissions, external messages, task creation, and replanning.
