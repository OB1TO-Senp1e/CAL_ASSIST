## Decisions log

- D1 (iter 1): C1 identity scopes for calendar flow = `openid` + `email` (bare OIDC strings, NOT `userinfo.*` URL scopes). The v2/userinfo endpoint answers to the `email` scope; this keeps externalUserId (email) working while dropping `userinfo.profile` and the broad `calendar` scope.
- D2 (iter 1): Google **login** strategy (`src/auth/google.strategy.ts`, scopes `openid email profile`) is out of C1 scope: it is the standard minimal "Sign in with Google" request (profile needed for display name) and uses no `www.googleapis.com/auth/*` URL strings. Grep acceptance for C1 targets `www.googleapis.com/auth/...` scope strings + userinfo scopes only. Logged here rather than silently broadening/narrowing.
- D3 (iter 1): `prompt=consent` gate: connection service looks up existing connection row; sends consent only if row missing or refreshToken null/empty (i.e. first connect or re-auth after token loss). `getAuthUrl` becomes async.
- D4 (iter 1): Callback stores the **granted** scope list returned by Google (token response `scope` field, space-delimited), not the requested list, so C1's partial-grant check is meaningful and `scopes` in DB reflects reality. Partial grant missing any requested scope → user-facing error.
- D5 (iter 1): Outlook/Apple adapters keep their own provider scopes (not Google policy) but must conform to the updated `handleCallback` return shape (`scopes: string[]`).
- D6 (iter 1): Lint protocol — repo's `npm run lint` auto-fixes and reflows the entire tree (CRLF/prettier baseline is dirty). Verification in this loop = `npx eslint --quiet <changed paths>` + full jest + tsc. Documented in iteration log.
- D7 (iter 1): Google **login** passport strategy left at `openid email profile` (needed for display name at signup; standard minimal login scopes; not part of calendar connection flows). See D2.
- D8 (iter 2): Key policy — production: missing/invalid OAUTH_TOKEN_KEY = boot failure (fail fast). Dev: boot succeeds with a warning but `encrypt()` throws ServiceUnavailable, so a calendar connect fails loudly rather than silently storing plaintext (safest option per rules; logged as decision).
- D9 (iter 2): `decrypt()` passes through non-"v1:" values so pre-migration plaintext rows keep working during rollout; the migration script closes the window. New writes are ALWAYS encrypted (no plaintext can enter going forward once a key exists).

Owner can revisit if a legal-hold requirement emerges (HUMAN note for policy review).
